## 2. Project summary

A web system for **Jhunlea Photography & Printing** (Philippines). It handles printing orders (with file uploads), photography package browsing and bookings (with optional photo printing), schedule confirmation, request tracking with reference numbers, **face-to-face** payment recording, owner management tools, and a restricted AI customer assistant.

This is a **new system built from scratch**. Only build from the spec and from files that really exist. Never claim a file, table, route or feature exists unless you have checked it.

`php artisan migrate:fresh --seed` wipes the database. Use it only on a throwaway local database, never on one that has real data.

### Running the tests safely

The tests wipe and rebuild every table they use (`RefreshDatabase`). They must only ever run on an in-memory SQLite database, never on the `jhunlea` MySQL database. This once went wrong: a terminal had the `.env` values exported as environment variables, and the tests ran against the real database.

- Run the tests in a **clean terminal**. Never export or load `.env` values into the shell (no `set`/`$env:` of `APP_`, `DB_`, `CACHE_`, `SESSION_` ... values, and no tool that loads `.env` into the terminal). Laravel reads `.env` by itself.
- Check before running: `Get-ChildItem Env: | Where-Object { $_.Name -match '^(APP_|DB_|CACHE_|SESSION_|MAIL_|QUEUE_)' }` (PowerShell) must show **nothing**. A terminal that shows any of them is not safe; close it and open a new one. If they come back in every new terminal, remove them from Windows "Edit the system environment variables" (User and System).
- Two layers protect the database. `phpunit.xml` forces the test values (as `force="true"` env entries **and** `<server>` entries, because Laravel reads `$_SERVER` first). `tests/Support/TestDatabaseGuard.php` checks the result in `tests/TestCase.php::createApplication()`, which runs before `RefreshDatabase`.
- If you see **"Refusing to run tests: this would touch the database ..."**, the guard stopped the run before anything was touched. Do not work around it: open a clean terminal. Every feature test must extend `Tests\TestCase` and must never override `createApplication()`; a unit test checks this.
- **On real MySQL (Phase 9B, `docs/MYSQL_TESTING.md`):** `php -d memory_limit=1G vendor/bin/phpunit -c phpunit.mysql.xml --testsuite MySql` (races, SQL behaviour, speed) and `--testsuite Unit,Feature` (the whole suite on MySQL). Only the empty local database `jhunlea_test` is used: `phpunit.mysql.xml` forces it and sets `JHUNLEA_MYSQL_TESTS=1` (`phpunit.xml` forces that marker empty), and the guard then accepts only testing + local MySQL + a configured AND live database name ending with `_test`. `tests/MySql` (base class `Tests\MySqlTestCase`: `migrate:fresh` once, every table emptied before each test, no wrapping transaction) never runs in the normal suite. A test that drops, alters or truncates a table calls `$this->changesSchema()` (MySQL commits DDL at once, so the next test starts from a fresh migration). The race worker `jhunlea:race-worker` lives in `tests/` and exists only in the testing environment.

## 5. Folder conventions

```
app/
  Enums/                 PrintingOrderStatus, BookingStatus, PaymentStatus, UserRole ...
  Http/Controllers/
    Public/              landing, services, packages (no login)
    Auth/                login, register, password reset
    Customer/            customer-only controllers
    Owner/               owner-only controllers
  Http/Middleware/       EnsureRole
  Http/Requests/         Form Request validation classes (one per form)
  Models/
  Policies/              record-level access (customer owns record)
  Services/              business logic: ReferenceNumberService, PricingService,
                         ScheduleConflictService, PaymentService, StatusTransitionService
resources/views/
  layouts/               public, auth, customer, owner
  components/            ui/* (button, badge, card, input, modal, toast, empty-state, stepper, timeline)
  public/ auth/ customer/ owner/ errors/
routes/web.php           grouped: public, auth, customer (prefix /my), owner (prefix /owner)
design/                  Stitch reference only; never served to users
```

Rules:
- Controllers stay thin: validate with a Form Request, authorize with a Policy, call a Service, return a view or redirect.
- No business logic or database queries inside Blade files.
- Use Enums for statuses and roles, never raw strings scattered in code.
- Reusable UI goes into Blade components; do not copy the same markup across pages.

## 6. Roles and access (exactly two roles)

| Role | Value | Can do |
|---|---|---|
| Print Shop Owner | `owner` | Manage services, packages, themes, schedule, all orders and bookings, prices, payments, customers, reports, settings |
| Customer | `customer` | Browse, submit printing orders, request bookings, see **only their own** requests and files, use the assistant, edit own profile and appearance |

- Public registration always creates `customer`. The owner account is created only with `php artisan jhunlea:create-owner` (hidden password prompt, refuses an existing email, asks for confirmation if an owner already exists). There is no setup screen.
- `users.role` is cast to `App\Enums\UserRole` and is **never mass-assignable**; server code sets it directly.
- Enforce access on the server: the `role` middleware alias (`role:owner`, `role:customer`, class `App\Http\Middleware\EnsureRole`) for route groups and Policies for every record and file. Guests go to login, a signed-in user with the wrong role gets 403. Hiding buttons is not security.
- Route groups: `auth` + `role:customer` for `/my/*`, `auth` + `role:owner` for `/owner/*`. After login, owner goes to `/owner` and customer to `/my/dashboard` (`UserRole::home()`).
- Customers can never: set owner-controlled statuses, set final prices, confirm their own bookings, or record payments.
- No Super Admin, Staff or other roles unless the team explicitly approves.

## 7. Business rules (must never break)

1. Submitting a request does not mean it is accepted.
2. A requested timeslot is not a confirmed appointment. Store and show **Requested** and **Confirmed** separately.
3. Show **Estimated** price and **Confirmed** price separately.
4. Payments are made outside the system: cash or GCash at the shop, or (since 10B) GCash sent to the shop with its reference number in Messages. The system records payments; it never processes them online. No checkout, no gateways.
5. Booking status, printing production status and payment status are separate fields.
6. A booking can be completed while its prints are still in production.
7. Customers see only their own records and files.
8. AI recommendations are suggestions, not bookings or quotations.
9. The chatbot uses only data configured in the system; it never invents prices, inclusions, schedules or policies.
10. Every status change is saved in the status history (who, when, from, to, note).
11. Never mark something as paid automatically. Only a recorded payment changes the paid amount.
12. Never charge printing twice when prints are linked to a booking.

Standard notice text (since Phase 10G, `PaymentRules::NOTICE`): "Pay at the shop in cash or GCash, or send GCash and the reference number in Messages. No online checkout." The older "Payment is made face-to-face at Jhunlea Photography & Printing." no longer matches the 10B rules and is not used anywhere.

**Money wording (Phase 6A):** only "Recorded payments" (what the shop actually received; voided ones never count; `PaymentLedgerService::totals()`) and "Awaiting payment" (a confirmed price with no recorded payment; `awaitingOrders()`/`awaitingBookings()`). Until Phase 8: never "revenue", "sales", "profit" or "income", and no average, growth or comparison figures. **From Phase 8 (walk-in logging and income reports, see `docs/DEVELOPMENT_PLAN.md`): the owner reports may say "Income", which is exactly the sum of recorded, non-voided payments in the chosen Manila days, and may show the average per transaction and a comparison with the previous period. "Revenue", "sales" and "profit" stay forbidden (the shop does not track costs); the quick counter flow is called "Quick walk-in"; voided payments stay visible with their reason but never count; estimates are never counted; "Awaiting payment" is never added into income. Update any test or view text that still bans these words when Phase 8 is built.** Otherwise the two figures are never added into one total. The reports page (`/owner/reports`, `ReportService`) counts requests CREATED and payments RECEIVED in a period of Manila days; its "Awaiting payment right now" is not limited to the period. The customer directory (`/owner/customers`, `CustomerDirectoryService`) lists customers only (an owner's id answers 404) and is read only. Notification preferences are cancelled (in-app only, no email or SMS channel). Hours and booking rules stay in the Schedule editor; Phase 6B settings only link to it.

**Settings, upload limits and FAQ (Phase 6B):** `App\Support\ShopSettings` is the ONE class that reads the business info and the six upload limits (`printing_max_file_mb`, `printing_max_total_mb`, `printing_max_files`, `booking_max_image_mb`, `booking_max_images`, `booking_max_total_mb`): the owner's saved value in `shop_settings` (one row, id 1, written only by `ShopSettingsService` under a row lock), else the starting default in config, and never more than `App\Support\ServerUploadLimits` allows (per file: upload_max_filesize; per order total: post_max_size minus 2 MB; count: max_file_uploads; 0, -1 or unreadable means a fixed ceiling of 100 MB / 50 files). A value above the server's maximum is capped when read and the Settings page says so. Never read `config('printing.max_*')` or `config('booking.max_image*')` anywhere else (a test fails if you do). The accepted file TYPES stay fixed in config. The Settings page only SHOWS the opening hours and booking rules (the Schedule editor changes them) and states the fixed payment rules without switches. The footer (since 10G `<x-layout.site-footer>`, public and customer layouts) shows the shop's contact details only when set, and the FAQ link only when a question is published. `faqs` positions are kept 1..N by `FaqService` (the only writer) under the same settings row lock. **Phase 7 (the assistant) will read the published FAQs from the `faqs` table.**

**Scheduling (Phase 10A; decided by the lead developer, do not change without her):**
- **Photoshoot hours are not the shop's hours.** `availability_rules` (the Schedule editor, "Weekly photoshoot hours") decides when a photoshoot can be booked and is the ONLY thing that drives the slots. The shop's own opening hours are one display text, `shop_settings.opening_hours` (Settings, Business info, up to 200 characters; `ShopSettings::openingHours()`), shown in the public footer and given to Lumi as written. The migration pre-filled it once from the rules. When the text is set, Lumi and `CodeAnswers` give it as written and say "inside / outside the photoshoot hours" for the computed part; they never work out "open now" from the text. When it is empty, the weekly rules are the only hours known and the older "The shop is open now" wording is used. (`OwnerPresence::awayNotice()` still words the away notice from the weekly rules.)
- **THE holding rule, in one place:** `PhotographyBooking::scopeHoldingTime()` (the query) and `holdsTime()` (its PHP twin for a loaded booking). A booking holds time when it is Confirmed or Completed; or Requested with `hold_expires_at` in the future and its time still ahead; or Proposed with `hold_expires_at` in the future and the PROPOSED time still ahead. The time held is `heldStart()` to `heldEnd()` (the proposed time for a proposal; the time first asked for is given up while a proposal is open). `ScheduleConflictService` (`conflictsFor`, `isFree`, `blockingBetween`, `mostAtOnce`), `AvailabilityService`, `ScheduleImpactService` and the daily limit all read these two methods and nothing else decides. A hold that ran out simply stops holding (worked out at query time: no cron, no stored status); the request stays Requested for the owner, who still sees it as a competing request. **Phase 10B adds "Awaiting downpayment until downpayment_due_at" to these two methods only.**
- **Hold length:** `booking_settings.request_hold_hours` (default 48, 1 to 720, Schedule editor). Set by `BookingService::place()` (now + hours), by `propose()` (the proposed time) and again by `askForAnotherTime()` (the first time, only when it is still ahead and nobody else holds it; otherwise no hold). Cleared on confirm, accept, reject and cancel.
- **No double hold:** `place()` takes the schedule lock inside its transaction and checks the time again there. The loser reads "Someone just requested this time. Please choose another." (`SLOT_JUST_TAKEN_MESSAGE`, whenever another booking holds the time; a time the schedule simply does not offer keeps `SLOT_TAKEN_MESSAGE`); the wizard keeps every other answer. `propose()` and `askForAnotherTime()` take the schedule lock too.
- **Lock order (the same everywhere, so nothing can deadlock):** 1. the schedule lock (`booking_settings` row 1), always FIRST; 2. the customer's `users` row (`place()` only); 3. the booking row; 4. the reference counter, then the inserts and the audit chain head. Nothing that holds a booking, customer or counter row asks for the schedule lock afterwards. `PaymentService` takes only the booking row and the PAY counter. `WalkInController::storeBooking` takes the schedule lock BEFORE it creates a new walk-in customer (that writes an audit row).
- **Expired (derived, never stored):** a Requested booking whose start has passed, or a Proposed one whose proposed start has passed (`isExpired()`, `scopeExpired()`, `scopeWaiting()` = not expired, `statusLabel()`). It holds no time, does not count toward the 3 open requests (`BookingService::atRequestLimit()` counts `waiting()`), shows a gray "Expired" badge (`<x-ui.status-badge :expired>`) and "This request was not confirmed before its time." to both sides, can never be confirmed, and is rejected by the owner or cancelled by the customer. The owner's list has an Expired tab (`?status=all&expired=1`).
- **One studio:** `concurrent_sessions` is always 1: not fillable, not in the editor or its request, written as 1 on every save, read as 1 by `BookingSetting::current()` whatever an old row holds. The column stays. `mostAtOnce()` still counts.
- **Daily limit:** `booking_settings.max_sessions_per_day` (empty = no limit, default empty, 1 to 50). Bookings that hold time count, by the Manila day of `heldStart()`. A day at the limit offers no time and reads "Fully booked". `confirm()` treats it as one more reason that "Confirm anyway" sets aside; a walk-in needs its own tick "Over the daily limit, book anyway" (`over_daily_limit`), which never sets aside a clash or a passed time.
- **People:** `photography_packages.min_people` (default 1, 1 <= min <= max, package form "Fewest people in the shoot"). One rule for the customer and the walk-in form: `BookingService::groupSizeFits()` and `groupSizeMessage()` ("Couple Session is for 2 people.", "Family Portrait is for 2 to 6 people."). The wizard's field starts at the minimum and is read-only when min = max. Cards say `fitsText()`: "2 people", "2-6 people", or "Up to 6 people" when the minimum is 1.
- **Time choice:** the step stays 30 minutes. `AvailabilityService::overview()` gives every day its state (`open`, `closed` "No photoshoots on this day.", `full` "Fully booked.", `no_fit` "No time long enough for this package on this day.", `none`) and the not-available stretches of the photoshoot hours (held time with its buffer, and time that is too soon); `slots()` is its flat list. The slots endpoint adds `info` and each slot's `ends` and `period`; the wizard shows a day timeline (striped "Not available", never who booked), start times grouped Morning / Afternoon / Evening with "ends 10:30 AM" under each, and "Times that are already requested or booked are not shown." A day without times can be opened to read why.
- **Schedule changes are safe:** `ScheduleImpactService` lists the bookings that HOLD time (confirmed sessions and held requests and proposals, at the time they hold) as the ones the owner must tick "Save anyway" for, when new photoshoot hours, a blocked date, a longer buffer or a lower daily limit would affect them; requests that hold nothing are information only. Nothing is ever cancelled or moved, by a setting or by the migration.
- **The migration** only adds columns and fills them: old open requests get a 48-hour hold from the moment of the migration only when their time is still ahead and no confirmed booking or older open request already holds it (the oldest wins; two old requests must not both hold one time, or neither could be confirmed).

**Walk-in foundation (Phase 8A):** a walk-in customer is an ordinary `users` row with `role = customer`, `is_walk_in = true`, a name, an optional phone (registration's own rule) and NO email or password (both columns are nullable since 8A; the unique index on email stays, NULLs are allowed). A walk-in can never sign in or reset a password (`LoginRequest`, the reset broker and `NewPasswordController` all add `is_walk_in = false`) and is never notified (`NotificationDispatcher` skips them in its one recipient query). `is_walk_in` is never fillable; `WalkInCustomerService` creates them, and the counter forms search existing customers (name or phone) before adding one. Every printing order and photography booking has `source` (`App\Enums\RecordSource`: `online`, the default and every older row, or `walk_in`), never fillable, shown as a "Walk-in" badge (`<x-walk-in.badge>`) on the owner lists, details, the schedule calendar and the overview, and filterable on both lists (`?source=`) and in the customer directory (`?type=walk_in|online`). Two services do the counter work so Phase 8B can call them inside its own transaction: `App\Services\WalkIn\WalkInOrderService::place()` (a walk-in printing order is NEVER saved unpaid: the order, source walk_in, created Accepted with its confirmed price and its first history row "Created at the counter", its optional files, its full payment through `PaymentService::record()` and then the usual owner move Accepted -> Processing ("Paid at the counter; printing starts.") are one transaction; the price is the catalog price from PricingService or one the owner types, kept with who set it and why in `snapshot.counter` and in the history note) and `WalkInBookingService::place()` (status Confirmed, under the same schedule lock as `confirm()`; a clash is never allowed, a passed time is never allowed, the minimum notice and the advance window do not apply at the counter, opening hours and blocked dates apply unless "confirm anyway"; the price is optional and the booking is paid on the day with the usual flow). Each counter form carries a one-time `counter_token` (unique column on both tables), so a double click or a retry saves one record; a new walk-in customer is created in the same transaction, so a refused form leaves no stray customer. Routes: `/owner/printing-orders/walk-in/new` (POST `/owner/printing-orders/walk-in`, saved screen `/{order}/walk-in-saved`, live price `/walk-in/price`), `/owner/bookings/walk-in/new` (POST `/owner/bookings/walk-in`, free times `/walk-in/slots`), `/owner/walk-in/customers` (JSON search), each with its own `owner-walkin-*` throttle.

**Counter (Phase 8B):** `/owner/payments` ("Payments and counter") is the counter; no sidebar item was added. `App\Services\Counter\CounterService` is read only: `search()` (orders and bookings by PR-/PB- reference with or without the hyphen, customer name or phone, booking contact number; % _ \ literal; 8 of each), `blocker()` (the plain reason a record cannot be paid now: closed, already paid, no confirmed price, ₱0.00, not accepted or confirmed), `describe()`, and the two queues `readyForPickup()` (?ready=) and `awaitingPayment()` (?awaiting=, the ledger's awaiting rule as one UNION, oldest first). `CounterController` (owner only, throttles `owner-counter-search`, `owner-counter-target`, `owner-counter-record`, `owner-payment-receipt`) records through `PaymentService::record()` only, with the amount the owner confirmed as `expected_amount`; there is no amount field and no token (the payments unique index already refuses a second recorded payment: "Already paid"). `cash_tendered` only works out the change, is never stored, and cash below the full price is refused (never a partial payment). **Income report (Phase 8C):** the Reports sidebar item opens `/owner/reports/income` (`owner.reports.income`); the Phase 6A requests report stays at `/owner/reports` and both pages share a tab bar (`owner/reports/_tabs`). Income is EXACTLY the ledger's total: `App\Services\Reports\IncomeReportService` (read only) calls `PaymentLedgerService::totals()`, `recorded()`, `inPeriod()` (new, every payment of a period) and `listing()` (new, the ledger rows unpaged; `payments()` pages it), so the report and the ledger cannot drift apart; a test proves report = ledger = sum of the listed recorded rows for every view. It returns income, count, average, Cash and GCash, Online and Walk-in (by the paid record's `source`, removed records included), Printing and Photography, the top 10 services and packages plus "Other" (catalog names, removed ones included), income per hour (a day), per day (a week, a month, a custom range up to 62 days) or per month (all time, longer ranges), voided count and amount apart (never counted), "still awaiting payment" (the ledger's awaiting rule, RIGHT NOW, never income) and the previous period (same length; the calendar month before for Monthly; a zero previous total says "No income in the previous period", never divides by zero). All grouping is in the database (fixed queries; Manila local time in SQL: SQLite `strftime(..., '+480 minutes')`, MySQL `DATE_FORMAT(DATE_ADD(..., INTERVAL 480 MINUTE))`; Manila has no daylight saving). Worked-out columns (source, item, time slot) are computed in an inner query and grouped by name in the outer one (`IncomeReportService::grouped()`): MySQL's ONLY_FULL_GROUP_BY refuses a GROUP BY on an expression with a subquery, and the SQLite tests cannot catch that. `IncomePeriod::resolve()` is the one period rule: Daily, Weekly (Monday to Sunday), Monthly, Custom (no dates = this month to today), All time; never past the current period. `IncomeReportRequest` validates every value and sends anything invalid back to the default view with "Your usual view is shown.". The chosen Daily, Weekly or Monthly view is remembered in `users.report_view` (default daily, not fillable, written only by `ReportViewPreference`). Charts are CSS in Blade (`<x-report.bars>`, `<x-report.split>`; `.chart-a` brand red, `.chart-b` ink or light gray with a stripe so color is never the only difference), each with `role="img"` and a table. The end-of-day summary (`owner.reports.end-of-day?date=`, a standalone A4 page like the 8B receipt) lists the day's payments, the voided ones apart, Cash and GCash, walk-in and online counts, awaiting payment and "Prepared from the system's payment records. Not an official document."; no cash count, variance or closing. The CSV (`owner.reports.csv`, same query values, streamed, UTF-8 with BOM, 13 columns, voided rows with status Voided, a leading apostrophe before = + - @ tab or CR) never touches the disk. "Print report" prints only `#income-report` in black on white (app.css print rules). Throttles: `owner-income-report`, `owner-income-end-of-day`, `owner-income-csv`. `Money::cents()` and `Money::compact()` were added for the charts.

**Audit trail (Phase 8E):** `audit_logs` is append-only: one row per important action, written by `App\Services\Audit\AuditLogger::record()` ONLY, inside the action's own transaction after the change succeeds (a rolled-back action leaves no row; a failure to write fails the action). Actions without a transaction (sign-in, CSV, end-of-day, receipt) log in their own transaction and only log a failure. Actions are the enum `App\Enums\AuditAction` (label, filter group, the ONLY meta keys it keeps: amounts in cents, method, statuses, old/new price, reason up to 200, counts, period). Never logged: message bodies, GCash references, passwords, tokens, keys, session ids, phone numbers, email addresses (the shop's address, phone and email settings log only that they changed), file names, the AI's prompts or answers; every string is passed through the `Redactor`. Hooks (one call each): `PaymentService` record/void; `StatusTransitionService` and `BookingTransitionService` `writeHistory()` (every real status move; payments and prices log themselves), `changePrice()`, `recordCounterOrder/Booking()`; `WalkInCustomerService::create()`; `ScheduleEditService` (hours, rules, block, unblock; only when something changed); `ShopSettingsService::write()`; `FaqService`; the catalog controllers (no catalog service exists); `AccountService` (owner only: password, email, other devices); `LoginController` (owner sign-in) and `LoginRequest` (a failed sign-in to an OWNER email, at most one row per IP per 10 minutes, no email or password); `IncomeReportController` (CSV with row count, end-of-day); `CounterController::receipt` (once per payment per Manila day). Idempotent paths (the same price, the same publish state, a second delete, a refused double payment) write nothing. Each row keeps an actor snapshot (`actor_name`, `actor_role`; `actor_id` set null when the account is deleted; `system` in the console) and the subject by its own short type (`AuditSubject`, not the morph map). Tamper evidence: `hash` = SHA-256 of `prev_hash` and the canonical JSON of the row's fixed fields. The write lock is the single-row table `audit_chain_head` (id 1, `last_id`, `last_hash`; created by the 8E migration with the genesis hash): `AuditLogger` reads it with `lockForUpdate`, uses its `last_hash` as `prev_hash`, inserts the row and moves the head forward in the same transaction (no gap lock on `audit_logs`, no fork on an empty table; a missing head is recreated with the genesis). `AuditLog` refuses update and delete (model events and its `AuditLogBuilder`), no route edits or deletes. `php artisan audit:verify` walks the whole chain (cached result) and then compares the head with the newest row, so deleting the newest rows is detected too; the page checks the newest 200 rows and the head each view. Every catalog change (services, options, packages, themes: create, update, delete, publish) runs in one `DB::transaction` with its audit row. Real lock contention cannot be tested on SQLite. This makes tampering DETECTABLE, not impossible, for someone with direct database access. `audit:prune --dry-run|--force` (config `audit.retention_days`, 730) is never scheduled; it verifies first, writes a checkpoint row (`audit.pruned`, the pruned id and its hash as the anchor) and then deletes; it never touches `audit_chain_head`, which then points at the checkpoint. The page `/owner/activity` (`owner.activity.index`, throttle `owner-activity`) is reached from Settings (section 6; the Settings sidebar item stays highlighted, no new sidebar item): one sentence per row with the actor, Manila time, a link to the record while it exists (one query per subject kind), group chips, Today / Yesterday / Last 7 days (default) / All time / custom dates, a search (wildcards literal), pagination, the integrity line and Export CSV (`owner.activity.csv`, throttle `owner-activity-csv`, BOM, 8 columns, the 8C formula guard, the export itself logged first). Nothing is back-filled from before 8E.

**Accounts (Phase 10C; decided by the lead developer):**
- **Email verification:** `User` implements `MustVerifyEmail` (Laravel's own signed link, 60 minutes, `VerifyEmailNotification` with the shop's wording). After registering a customer is signed in and lands on "Check your email" (`/email/verify`: resend, change my email on the account page, sign out). Resend `POST /email/verification-notification` is limited to 3 per 10 minutes (`verification-send`). The link `/email/verify/{id}/{hash}` is `signed` and works only for its own signed-in account. An unverified customer may open only that page, the account page (`customer.account.*`) and sign out: the loop at the END of `routes/web.php` adds `verified` to every `role:customer` route except `customer.account.*` (no check anywhere else; `EnsureEmailIsVerified` runs before route binding, see `bootstrap/app.php`). Login sends an unverified customer to the notice with a friendly line. An email change on the account page clears `email_verified_at` and sends a new link. The migration marked every existing customer and the owner verified; `jhunlea:create-owner` creates the owner verified; the owner is never blocked. Walk-ins (no email) are never sent anything (`sendEmailVerificationNotification()` skips them). The `UserFactory` default is verified; use `->unverified()` for the other case.
- **Password reset by code:** `PasswordResetCodeService` is the ONE place. `POST /forgot-password` always answers "If an account exists for that email, we sent a code." (unknown emails and walk-ins get the same answer and no email) and goes to `/reset-password?email=`. The code: 6 digits from `random_int`, stored only as a hash in `password_reset_codes` (one row per user: a new request replaces it), valid 10 minutes, burned after 5 wrong tries, deleted once used. The code, the new password and its confirmation are typed on one page; a wrong or expired code reads "That code is not valid or has expired ...". Limits: per IP by the route throttles (`password-email`, `password-reset`), per email 3 requests and 10 tries every 10 minutes (RateLimiter, sha1 of the email). Success saves the password, replaces the remember token, deletes EVERY session of that user, deletes the code, audits an owner's change and sends `PasswordChangedNotification`. The old link route `/reset-password/{token}` only redirects to Forgot password. Laravel's `password_reset_tokens` table is no longer used.
- **Phone:** `App\Support\PhilippineMobile` is the ONE rule for registration (required), the account page (optional), a new walk-in customer (optional) and a booking's contact number (required): "0917 123 4567", "09171234567", "+63 917 123 4567", "63-917-123-4567" and brackets or dots are accepted; it is stored as `09XXXXXXXXX`. Landlines and foreign numbers are refused. Old rows are never rewritten. The walk-in picker also finds a stored number by the digits typed with spaces or +63.
- **Consent:** registration needs the `terms` checkbox ("I agree to the shop's terms and the processing of my data under the Data Privacy Act of 2012 (RA 10173)"), never pre-ticked, linking to `/terms` (`public.terms`, throttle `public-terms`, linked in the public footer): what is collected, why, who sees it (the owner; the AI provider for Lumi messages, redacted), how long, and how to ask for correction or deletion (through the studio; there is no delete button).
- **Profile pictures:** `AvatarService` is the ONE writer of `users.avatar_path` (not fillable): JPG, PNG or WEBP up to 2 MB, checked by extension AND the MIME read from the file (`UploadCheck`), stored on the `public` disk under `avatars/` with a random name; a new one deletes the old file; Remove deletes it. Routes `POST` / `DELETE {my|owner}/account/avatar` (own throttles), errors in the `avatar` bag. Shown by `<x-ui.user-avatar>` (initials when there is none; `User::avatarUrl()` is always null for a walk-in) in the top bar, the account page, the chat bubbles (`ChatPresenter` adds `avatar` {url, initials} for customer and owner messages, never for Lumi) and the owner's customer list and detail. Needs `php artisan storage:link`.
- **Mail:** real email goes through SMTP (Gmail with an App Password, `docs/EMAIL_SETUP.md`); local work keeps `MAIL_MAILER=log` and reads links and codes from `storage/logs/laravel.log`. Tests use `Notification::fake()` and never send. `jhunlea:preflight` FAILs on a `log`/`array` mailer in production or a missing `MAIL_FROM_ADDRESS`.

**Interface rules (Phase 10D; the final polish, no business rule changed):**
- **Pop-ups only where they help.** A pop-up appears only (a) to CONFIRM an action that is important, costs money or cannot be undone, (b) to show the RESULT of an action, or (c) to explain something the first time it matters. Never on page load for advertising, never two at once, never blocking reading. Confirmations are the one dialog, results are toasts, explanations are an inline tip or a one-time hint.
- **ONE confirmation dialog:** `<x-ui.confirm>` (in every layout), never the browser's `confirm()`. A form or a submit button asks first when it carries `data-confirm="Title?"` (plus `data-confirm-text`, `-detail`, `-ok`, `-cancel`, `-danger`); the button is named by the action ("Reject booking" / "Go back"). Esc, the backdrop and the browser's back button close it; focus is trapped and returned; a bottom sheet on phones. Without JavaScript the form simply posts and the server decides as always. The older `<x-ui.modal>` dialogs (catalog delete, the two-step Record payment) stay: they are already confirmations in the same style.
- **ONE result message:** `<x-ui.toast>`: `status` (success), `warning` and `error` flashes, `$dispatch('toast', {message, variant, link})` and the live-update toasts. At most three at once, about 5 seconds (8 for a page flash), an error stays until closed, `role` status or alert, and a link only to a page of this site.
- **ONE form grid:** `class="form-grid sm:grid-cols-2"` (app.css): every field is a subgrid of label, control and help, so the inputs of a row line up even when a label wraps or a help text is longer. `<x-ui.field>` carries `ui-field`. Date inputs always fill their column.
- **ONE time field:** `<x-ui.time-picker>` (no scrolling wheel): a button showing "9:00 AM" opens a grid of times in AM and PM tabs; arrows, Home, End, Enter and Esc work. Its `<select>` is the form control and posts the same `H:i` the server always expected, so validation is unchanged and without JavaScript the select is the field.
- **ONE package card and ONE price:** `<x-package.card>` (landing, list, related; `<x-package.media>` and `<x-package.chips>` are reused by the finder and the booking wizard) and `<x-ui.price :text="$model->priceText()">` (the amount in one size and weight, the note after the dash as small muted text on its own line; `priceText()` stays the one place that words a price). A package without a photo gets `<x-ui.image-placeholder :label :category>`, never an empty box.
- **Public image addresses are root-relative** (`App\Support\PublicFile::url()`, used by `PackageImage::url()`, `Theme::imageUrl()` and `User::avatarUrl()`): `/storage/...`, so photos load under any host (127.0.0.1, a LAN address, a phone). Never build one from APP_URL.
- **The payment line:** `PaymentRules::shortLine()` is the ONE short, current sentence (top bar of the public pages with a "Details" link to the FAQ or the terms, footer of the customer pages). Since 10G the public footer no longer carries the old face-to-face sentence (the top bar already says it); the customer footer shows `shortLine()` in its brand column. No page repeats it as a callout and the splash does not show it.
- **Navigation:** a top item never wraps (`whitespace-nowrap`; `short` labels below 1280px; the customer bar has no icons) and the active item differs by background and colour only. The owner sidebar folds to icons with the header button (`sidebarToggle`, localStorage `owner-sidebar`, applied before the first paint).
- **Floating buttons:** Chat and Ask Lumi are a round icon on phones, hidden while a field in the page is focused or a dialog is open; the owner pages keep bottom room so the button never covers the last field.
- **Speed:** Speculation Rules in `layouts/app` prefetch same-site GET links on hover or touch ("moderate"). Excluded: logout, `/email/verify/*`, `/reset-password/*`, files and booking images, CSV, receipt and end-of-day pages (they are logged), a notification's own address and the chat pages (opening them marks things read), and any link with `data-no-prefetch`, `download` or `target="_blank"`. A new GET route whose opening changes something must be added to that list. Cross-document View Transitions fade the page; `.site-header` and `.owner-sidebar` keep their own names. `FontPreload` preloads the two text fonts and the icon font from the build manifest. Every submit button goes busy and cannot be pressed twice (`data-busy`; add `data-no-busy` to a form that must not).
- **Live updates (polling, no WebSockets):** `GET /my/live` and `GET /owner/live` (`LiveController`, `App\Services\LiveStamp`; auth, role, `verified` for customers, 30 a minute) answer `{stamp, unread, latest}`: the stamp is a hash of the count and newest change of what that person can see (a customer: only their own orders, bookings, payments and notifications; the owner: all records and their own notifications). `liveUpdates` (polish.js) polls every 15 seconds while the tab is visible and backs off to 2 minutes on errors. On a change it refreshes the bell, toasts the newest notification and swaps the parts marked `data-live` by fetching the same address. A page being typed in, or with a dialog open, is never swapped: it gets "This page was updated. Refresh". Only the lists, details and dashboards named in the two layouts are `data-live="page"`; never a wizard or a settings form.
- **Landing and settings:** the landing page shows the first 6 published FAQs and "Visit us" (address, shop hours, phone, email, Facebook, a lazy Google Maps embed of the address from `ShopSettings::map()`), each only when set. `shop_settings.facebook_url` (https on facebook.com or fb.com only) is in Business info, the footer and Lumi's knowledge.
- **Photo viewer:** `<x-ui.lightbox>`; a link `<a href="photo" data-lightbox="group" data-alt="...">` opens in it (previous, next, "2 of 5", Esc, arrows, swipe, focus trap). Without JavaScript the link opens the photo.
- **Customer guidance:** `<x-ui.next-steps :record>` (`App\Support\NextSteps` only WORDS the real status) on the sent and placed pages and on the customer's booking and order pages; `<x-ui.countdown :until>` on a downpayment deadline for both sides (red under 24 hours); `<x-ui.copy :text>` for reference numbers and the GCash number; `<x-ui.hint name>` for the three one-time tips (localStorage `hint-<name>`).
- **Calendar and chat:** a request or offered time that holds its time (the one 10A rule, `holdsTime()`) shows as "Held request" with a thicker dashed border and a lock; awaiting downpayment is dotted violet; the legend says who holds time. The chat away notice gives the shop's opening hours text as written when it is set (`away_notice_hours`) and never works out "open now" from it.
- **Suggested FAQs:** `App\Support\FaqDrafts` words about 16 questions about using the system with the current settings; `POST /owner/faqs/suggested` (`FaqService::addSuggested()`) adds them UNPUBLISHED and skips any question already in the list. Same text in `docs/FAQ_DRAFTS.md`.

**Account page (Phase 6C):** `/my/account` (customers) and `/owner/account` (the owner, who now changes their own password here) share `AccountController`, `AccountService` and `<x-account.page>`. **Notifications (Phase 5B):** in-app only (database channel, written in the same request after the transaction commits; no email, SMS, push, queue or websocket). `NotificationDispatcher` is the ONE place that decides who is told what; StatusTransitionService and BookingTransitionService call it from their `writeHistory()`, so a notification exists only when a history row was written (a double click or a stale page that writes nothing notifies nothing). A failure to write one is logged without personal data and never breaks the action. Nobody is told about their own action. When the shop or studio cancels an order or booking, the customer is told (Phase 5C: OrderCancelledByShop, BookingCancelledByShop; the reason is never in the notice). The customer's combined history (`RequestHistoryService`, `/my/requests`) is a UNION ALL of two bound selects (kind, id, created_at) that the database sorts and paginates; the page's rows are then loaded with one query per kind.

**The shop's payment rules (Phase 10B, replacing the 5A "one full payment" rule; decided by the lead developer):**
- **Never changes:** the system only RECORDS payments; the owner records each one after receiving it (cash at the shop, or GCash the owner checked in the shop's GCash app); amounts are computed, never typed; voids need a reason and stay in the audit trail; an order or the photos are released (Completed) only when fully paid; never "revenue", "sales" or "profit". Nothing is ever recorded from the customer's side.
- **Settings** (Settings, "4. Payment rules", owner only, audited as `settings.payment_rules_changed`; read ONLY through `ShopSettings`; defaults in `config/payments.php`): Downpayment percent 50 (0 = none), Downpayment due days 3, Minimum hours to pay 24, Pay first from ₱300.00 (printing), Unclaimed after days 7, and the GCash name and number shown to customers (display only, kept out of the audit values). `App\Support\PaymentRules` is the ONE place that works the rules out (downpayment, deadline, what may be paid next, the sentences customers and Lumi read).
- **Payment kinds** (`payments.kind`, `App\Enums\PaymentKind`): `full`, `downpayment`, `balance`; every row before 10B is `full`. Unique index (payable_type, payable_id, kind, active): one active payment of each kind. `PaymentRules::options()` (and `PaymentService` on the locked row) allows: `full` only when nothing is active; `downpayment` only on a booking "Awaiting downpayment" with nothing active; `balance` only when an active downpayment exists and no balance. Printing orders take only `full`. Amounts: full = confirmed price; downpayment = percent of the price in centavos rounded UP to the whole peso, never above the price; balance = price minus the active downpayment. `expected_amount` stays the stale-page check of the chosen kind. GCash references stay unique across active payments.
- **Photoshoot downpayment:** confirming (or the customer accepting a proposal) goes to `awaiting_downpayment` when the price is above zero and the percent above 0, else straight to Confirmed. `downpayment_due_at` = shoot start minus the due days; when that is less than the minimum hours after the confirmation, confirmation + those hours; never after the shoot start (shown in Manila time). It HOLDS its time until the deadline (the one 10A holding rule). Recording the downpayment or the full price confirms it in the same transaction (`BookingTransitionService::confirmByPayment()`). The owner may "Extend deadline" (after now, no later than the start, reason, audited; under the schedule lock) or "Waive downpayment" (reason, audited; Confirmed, the full price due on the day). Past the deadline the SYSTEM cancels it ("Downpayment not paid by the deadline.", history `changed_by` NULL shown as "System", audit actor System, customer notified): `DownpaymentExpiryService::expireDue()` through `BookingTransitionService::expire()`, each booking in its own transaction with the row locked and re-read (a payment committed first wins), idempotent; run by `php artisan bookings:expire-unpaid` (scheduler every 15 minutes) and lazily by the `expire.downpayments` middleware on the dashboards, booking lists and details, schedule, counter, wizard and walk-in pages (works without cron). Voiding a downpayment is refused while its balance is active; voiding the downpayment of a Confirmed booking sends it back to Awaiting downpayment with a deadline of now + 24 hours (never after the start). A walk-in booking is never left awaiting: the owner records the downpayment or the full price in the same transaction, or waives it with a reason (audited); a price of ₱0.00 (or a 0% rule) needs neither.
- **Printing:** `printing_orders.requires_prepayment` is set when the shop accepts: ticked by itself from "Pay first from" or when the customer is flagged; the owner may tick or untick it, never for a flagged customer. Accepted -> Processing is refused while it is not settled ("Collect the payment before printing."). A customer may cancel an Accepted order while nothing is paid. `unclaimed` (owner only, from Ready for pickup): only unpaid and at least "Unclaimed after days" after the order last became ready (history); closed, never income, never awaiting; it sets `users.prepay_required` (walk-ins too; `PrepayFlagService`, audited), shown on the customer page with an owner "Clear" (audited).
- **Cancelling with money recorded:** the customer may cancel an awaiting booking any time and a confirmed one until 24 hours before; a recorded downpayment is non-refundable and stays income (the dialog says so). The SHOP must choose "Keep the payment (not refunded)" or "Refund: void the payment(s)" with a reason; a refund voids every payment (balance first) through `PaymentService::refundAll()` in the same transaction, audited as `payment.refunded`. The preset reason "Did not show up" is accepted only after the shoot's start time.
- **How to pay (customer):** on an order or booking with something due, the amount due now, the deadline, "Pay at the shop (cash or GCash), or send GCash to <name> <number> and send the reference number in Messages", and a button that types "Payment for PB-000123, GCash ref: " in the Studio chat (the customer sends it).
- **Income:** each payment counts on the Manila day it was recorded (a downpayment one day, its balance another); ledger, income report, end-of-day, CSV and dashboards still read the one `PaymentLedgerService`. "Awaiting payment" counts what is still DUE (a booking with its downpayment recorded counts its balance); bookings waiting for their downpayment are listed apart (counter "Awaiting downpayment", "Shoots today with balance due", overview and Briefing).
- **Lock order** (unchanged and extended): schedule lock -> customer row -> booking or order row -> PAY counter -> audit chain head. Expiry and payments on one booking serialize on the booking row; `WalkInController::storeBooking` takes the schedule lock and then the PAY counter before it creates a new walk-in customer (an audit row).

## 8. Status models

**Printing order:** `submitted` → `under_review` → `accepted` | `rejected` → `processing` → `ready_for_pickup` → `completed`. Also `cancelled`. Owner can request more information while in review (`needs_info` flag + message). Rejection requires a reason.

**Photography booking (since Phase 4A, App\Enums\BookingStatus):** `requested` → `confirmed` | `proposed` | `rejected` | `cancelled`; `proposed` → `confirmed` (customer accepts) | `requested` (customer asks for another time) | `cancelled` | `rejected`; `confirmed` → `completed` | `cancelled`. `confirmed` and `completed` always hold a slot; since Phase 10A a `requested` or `proposed` booking holds its time too while its hold lasts (section 7, "Scheduling"), and one whose time has passed reads "Expired" (derived, not a stored status). The customer never confirms a request. "Confirm anyway" can override the schedule rules (hours, notice, blocked day) but never a conflict and never a start time that has already passed. Changing the hours, settings or blocked dates never cancels or moves a booking; confirmed bookings left outside the new rules are listed and the owner must tick "Save anyway". (This replaces the earlier draft list.)

**Print production for a booking (only if prints were requested):** uses the printing order statuses on a linked printing order.

**Payment status (derived, since Phase 5A, App\Enums\PaymentStatus::derive()):** `awaiting_price` (no confirmed price yet), `unpaid` (a confirmed price above zero and nothing recorded), `downpayment_paid` (Phase 10B: recorded payments above zero but below the price; the balance is due), `paid` (recorded payments reach the price), `no_charge` (confirmed price exactly 0.00; nothing is due). It is derived from the SUM of the active payments. Never typed in a form and never stored. The amount due is always the confirmed price, never the estimate. Paid and no charge are "settled": only then may StatusTransitionService move an order Ready for pickup → Completed and BookingTransitionService move a booking Confirmed → Completed (the release gate). While a payment is recorded, changePrice is refused ("Void the payment first"). A payment row is `recorded` or `voided` (App\Enums\PaymentRecordStatus); a voided payment never counts. Orders take a payment from Accepted on, bookings from Awaiting downpayment on; never on Rejected, Cancelled or Unclaimed. A payment can be voided (reason required, kept in the payments table only) until the order or booking is Completed. The only smaller payments are a photoshoot's downpayment and balance (Phase 10B); a refund is only the shop's "Refund: void the payment(s)" choice when it cancels.

Allowed transitions live in one place (`StatusTransitionService` or the Enum) and are validated on the server.

## 12. Security checklist

- Hash passwords with Laravel's default hasher. Use Eloquent / query builder only (no raw string SQL).
- CSRF on every form (`@csrf`). Escape output with `{{ }}`; avoid `{!! !!}` for user data.
- Validate every input in Form Requests, including prices, statuses and IDs sent from the browser.
- Uploads: check extension, MIME and size on the server; store with generated names in private storage; never execute; serve via an authorized route.
- Policies on every customer record and file (prevent IDOR).
- Rate limit login, uploads and the AI endpoint.
- Secrets only in `.env`. Never commit `.env`. Never expose API keys in JS.
- Customer-facing errors never show stack traces (`APP_DEBUG=false` in production).

**Phase 9A (security pass; full audit in `docs/SECURITY_AUDIT.md`):**
- **Route matrix:** `tests/Feature/Security/RouteAccessMatrixTest.php` lists EVERY route with its access class (public, guest, signed_in, customer, owner, framework). A new route without a line fails the test: add it to `MATRIX`, and to `CROSS_USER` when it takes a customer's record. The test also checks each route's middleware, sends a guest and the wrong role everywhere, and proves another customer cannot reach a customer's records.
- **Another customer's record answers 403** (its policy); a conversation and a notification answer 404 on purpose (ConversationPolicy, own-rows lookup).
- **Throttles:** every route except `/up`, `/ui-kit` and the fallback has its own named counter, inline in `routes/web.php` (`throttle:N,1,name`), including the owner catalog, the owner order list and detail, logout and the guest form pages (9A).
- **Headers:** `App\Http\Middleware\SecurityHeaders` (web group): nosniff, `X-Frame-Options: SAMEORIGIN`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy` (camera, microphone, geolocation, payment off), HSTS over https only; a header the response set itself is kept. No enforcing CSP (Alpine needs eval; the Report-Only proposal is in the audit).
- **Session and hosts:** `session.secure` follows SESSION_SECURE_COOKIE, else is true exactly when APP_URL is https; `$middleware->trustHosts()` accepts only the APP_URL host outside local (password reset links can never carry a forged Host).
- **Files:** the private `local` disk has `serve => false` (no Laravel `/storage/{path}` routes); `storage/app/public/.htaccess` refuses scripts in the uploaded images folder (Apache).
- **Preflight:** `php artisan jhunlea:preflight` before hosting: read only, PASS/WARN/FAIL lines, exit 1 on any FAIL, never prints a key (only "set" or "missing") or a database error message. Checks for `App\Support\Preflight\PreflightProbe` are faked in `PreflightCommandTest`.

## 13. AI assistant rules (Phase 7)

- **Two conversations:**
  - **Ask Lumi:** the customer and the AI only.

## 15. Rules for AI coding agents

### Git rules for agents

- The developer handles ALL git write operations herself: creating branches, `git add`, `git commit`, `git push`, `git pull`, merging and untracking files. Claude Code (the agent) only writes code, runs tests, and reports.
- Read-only git is allowed: `git status`, `git diff`, `git log`, `git branch --show-current`, `git check-ignore`.
- Never run: `git add`, `commit`, `checkout`, `switch`, `merge`, `rebase`, `reset`, `stash`, `push`, `pull`, `fetch`, `rm`, or anything that changes history or the working branch.
- At the start of every task run `git branch --show-current`. If it is `main` or not the branch the developer named, stop, edit nothing, and tell her.
- Workflow: one branch per phase, reviewed by Claude in the chat; Claude's approval is final (no partner review, no Pull Request). After approval the developer merges the branch into `main` with `git merge --ff-only` and the next phase starts from that `main`. Large phases may be split into parts on the same branch with backup pushes. See `docs/GIT_WORKFLOW.md`.
- Never run `php artisan migrate:fresh`, `migrate:reset` or `db:wipe`, and never delete the developer's real accounts or data. Create your own QA users and delete only those.

### General rules

- Work only inside the current phase scope. Ask before adding features from later phases.
- Before editing a file, read it. Before adding a table, check existing migrations.
- Use the matching `design/<area>/<screen>/screen.png` and `code.html` as the visual reference, converted to Blade + Tailwind 4 + components.
- Prefer small, reviewable commits with clear messages.
- Report honestly at the end: what is done, what was tested, what is missing.
- Do not install Laravel Boost or other packages without the team's approval.
